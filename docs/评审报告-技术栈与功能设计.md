# 宠物之家 · 技术栈与功能设计评审

- 评审对象：仓库当前 HEAD（`8af36e5`）
- 评审范围：技术栈、功能清单、业务闭环、安全与工程质量
- 评审方式：读源码 + 读 SQL + 实测公网入口（只做了只读探测）

---

## 一、项目定位

宠物交易 + 养宠服务的全栈系统：C 端商城（选宠、AI 匹配、粮/用品下单、预约、问诊、社区）+ 自研管理后台（看板、14 项业务管理、RuoYi 系统管理、监控）。前端 57 个 Vue 文件（约 1.48 万行）+ 3.3 千行 JS；后端 17 个 `Pet*Controller` + 对应 Service/Mapper（Java 全量约 4.4 万行，含 RuoYi 框架）。

**一句话结论**：演示完成度很高，UI/交互与数据织得比较密；但"宠物交易"这条主线只走到「预约看宠」，**下单—支付—交付—售后**没有闭成环，且公网部署存在若干可直接利用的安全面。

## 四、设计亮点（值得保留）

1. **推荐不是伪 AI**：硬条件先过滤（类型/有小孩/预算），再逐维扣分（空间、活动量、护理等级、经验、噪音、月花费、粘人/独立），最后混合协同过滤与热度：有历史 `0.72/0.16/0.12`，无历史 `0.84/0.16`；结果附 `reasons / cautions / breakdown`，可解释性好。
2. **无结果也落库并归因**：按「类型 → 小孩 → 预算」互斥归因，前端能直接提示"最低价 X 元，超预算"，这是很多同类作品缺失的细节。
3. **AI 三处复用同一通道**：`chat` / `stream`（SSE，逐字返回）/ `parse`（自然语言→结构化问卷）/ `insight`（经营分析，喂真实看板数据）；60s 宠库摘要缓存、上下文截断 8 条、失败自动降级为规则，前端永远有内容。
4. **双 Token 作用域**：解决同源部署下"前台登录导致后台串号"的经典坑，`ensureScope` + 请求拦截器按 store 取 token 的做法是对的。
5. **验收靠真浏览器**：35 个 CDP 脚本覆盖权限门禁、多宽度导航、移动端图片审计、上传、AI 对话，比只写单元测试更贴近"能不能用"。

## 五、问题与修改意见

### P0 · 上线前必修（安全 / 资金）

**P0-1 Druid 控制台公网可达（实测确认）**
- 证据：`http://47.116.73.25/dev-api/druid/login.html` 返回 **200**；`SecurityConfig` 放行 `/druid/**`；`application-druid.yml` 里 `statViewServlet.enabled=true` 且账号口令写死；Nginx 两份 conf 都没有拦 `/druid`。
- 风险：任何人可看连接池、SQL 执行统计、URI 监控、Session，配合默认口令等于把数据库结构交出去。
- 建议（三选二以上一起做）：① 部署环境把 `stat-view-servlet.enabled` 设为 `false`；② Nginx 加 `location ^~ /druid/ { deny all; }`；③ 真要留着就改强口令 + `allow 127.0.0.1; deny all;`。

**P0-2 密码明文存储**
- 证据：`PlainPasswordEncoder.encode()` 直接返回原文；`sql/password_plaintext.sql` 把 `admin/ry` 改成 `admin123`、`md123` 改成 `123456`。
- 风险：库一旦被读（见 P0-1），所有账号直接可用；也违反等保/个保法基本要求。
- 建议：删掉 `PlainPasswordEncoder`，恢复 `BCryptPasswordEncoder`，写一次性迁移脚本把存量明文重新 hash；演示账号在 README 里给初始口令即可。

**P0-3 JWT 弱密钥**
- 证据：`application.yml` → `token.secret: abcdefghijklmnopqrstuvwxyz`（仓库可见）。
- 风险：可离线伪造任意用户（含 admin）的 token。
- 建议：`token.secret` 改为 `${JWT_SECRET}` 环境变量注入，长度 ≥ 64 的随机串；发版时轮换一次（会让现有登录态失效，可接受）。

**P0-4 数据库账号/口令入库**
- 证据：`application-druid.yml` → `root / 123456`；`改成明文密码.bat` 里也带口令。
- 建议：专用账号 `pet`（只授权 `ry-pet` 库），口令走环境变量；`改成明文密码.bat` 属于一次性运维工具，移出仓库。

**P0-5 AI 公开接口的"限流"名不副实**
- 证据：`SecurityConfig` 注释写"服务端有 IP 限流"，实际 `PetAiServiceImpl.waitTurn()` 是 `static synchronized` + 全局 `lastCallTs`——**所有用户共用一条 1.5s 队列**，既防不住刷（N 个请求排队照样打满），又让正常用户互相拖慢（一个人连续提问会卡住全站）。
- 建议：换成按 IP + 用户维度的令牌桶（Guava `RateLimiter` / Redis `INCR + EXPIRE`），例如游客 5 次/分、登录用户 20 次/分；同时对上游 429 做指数退避与熔断，并把"降级次数/成功率"打点。

**P0-6 订单金额由前端决定**
- 证据：`PetCartController.submit(List<PetCart>)` 直接取 `item.getPrice()` 乘数量累加；`pet-web/src/views/shop/cart/index.vue` 把前端价格原样提交；宠物粮目录 `FOOD_CATEGORIES` 是写死在前端的常量，后端**没有任何商品表**。
- 风险：改包即 0.01 元下单；后台"购物车管理"看到的也是伪造金额。
- 建议：建 `pet_goods`（SKU/价格/库存/上下架），下单只传 `goodsId + qty`，服务端查价算钱并落金额快照；支付前再校验一次。

### P1 · 业务闭环缺失（决定"是不是真系统"）

**P1-1 宠物本身买不了**
- 现状：`pet_info.status`（0 在售/1 已售/2 下架）全站没有任何地方改成 `1`；详情页只有「立即预约」，购物车只收商品。
- 影响：核心交易主线断在"预约"，无法体现"宠物交易系统"。
- 建议：加 `pet_order`（主表）+ `pet_order_item`（子表，可同时含宠物与商品）；下单时 `UPDATE pet_info SET status='1' WHERE pet_id=? AND status='0'` 做 CAS 占位，支付超时（如 30 分钟）定时任务释放；后台增加"宠物订单"菜单与交付状态（待交付/已交付/已退款）。

**P1-2 订单寄生在购物车表**
- 证据：`pet_cart` 同时是购物车和订单（靠 `order_no` 聚合、`pay_status/pay_method/pay_time` 挂在明细行上）。
- 缺失：订单金额快照、收货地址、运费、优惠、退款、物流、售后单。
- 建议：`pet_order` 存订单头（金额、状态、地址快照、支付流水号），`pet_cart` 只做购物车，结算时生成订单并清车。

**P1-3 支付是假的**
- 现状：`payOrder` 只更新 `pay_status`，任何人点"立即支付"即成功（幂等做了 `pay_status='0'` 条件，这点是对的）。
- 建议：至少二选一——接微信/支付宝沙箱走"下单→回调→验签→改状态"；或明确标注"线下付款 + 后台人工确认收款"，把 `pay` 接口限制为管理员/店员。

**P1-4 预约颗粒度太粗**
- 证据：表只有 `appointment_date`（+ 电话），无时段、无门店、无容量、无"同人同宠重复预约"校验；README 写的"选择门店与时间"与实现不符。
- 影响：一只热门宠物可被无限预约，门店排班无法落地。
- 建议：加 `store_id`、`slot_start/slot_end`、`UNIQUE(user_id, pet_id, slot_start)`；后台配置每店每时段容量。

**P1-5 C 端无法自助注册**
- 证据：`sys.account.registerUser = false`；登录页只有账号/密码/验证码，无注册、无找回密码；用户只能后台 Excel 导入。
- 建议：打开注册开关 + 登录页加注册入口（手机号/邮箱 + 验证码），或接微信扫码登录；注册默认角色固定为"普通用户"，不要复用后台角色。

**P1-6 没有商品中心**
- 证据：`views/shop/food/index.vue` 里 7 类目、商品、价格、营养信息全是前端常量；后台无对应管理页。
- 建议：建 `pet_goods` + `pet_goods_category`，后台加"商品管理"，前台改为接口拉取（配合 P0-6 一起做）。

**P1-7 社区互动共用 `pet_id` 列，唯一键有冲突风险**
- 证据：粮食评论/点赞复用 `pet_like`、`pet_comment` 的 `pet_id` 列，用 `target_type` 区分；但仓库 DDL 的唯一键仍是 `uk_user_pet (user_id, pet_id)`，没带 `target_type`。
- 影响：若线上索引未改，"宠物 5" 与 "粮食 5" 会共用一条点赞记录，出现"点了粮食却显示宠物已赞"或唯一键冲突报错。需核对线上 `SHOW INDEX FROM pet_like`。
- 建议：唯一键改为 `(user_id, target_type, pet_id)`；字段命名改 `target_id` 更贴切。

**P1-8 咨询/问诊没有会话**
- 现状：客服是"提交一条 → 后台回一条"，医生是单轮问答；用户端看不到自己的历史（记录只在后台）。
- 建议：加 `pet_chat_session` + `pet_chat_message`，前端做会话列表与多轮上下文；医生问答把最近 5 轮带进 prompt。

### P2 · 工程质量与可维护性

**P2-1 业务代码寄生在脚手架里**
- 证据：17 个 `Pet*Controller` 全在 `com.ruoyi.web.controller.system`；domain/mapper/service 塞在 `ruoyi-system`。
- 建议：新建 `ruoyi-pet` 模块，包名 `com.ruoyi.pet.{controller,service,mapper,domain}`，`ruoyi-admin` 只做启动与聚合。升级 RuoYi 时不会互相污染。

**P2-2 数据库不可复现**
- 证据：`sql/` 下 20 个 patch 脚本按日期堆叠；`pet_cart` 只有 `ALTER`/`INSERT` 没有 `CREATE TABLE`；`pet_like` / `pet_comment` 的 DDL 缺 `target_type`、`pet_comment` 还缺 `score`（代码都在用）；`pet_backup_20260930.sql` 只有 2 张表的建表语句。
- 影响：换台机器按 README 从 0 建库，建不出可用结构。
- 建议：引入 Flyway，写一份 `V1__baseline.sql`（完整 schema）+ 后续 `V2__order.sql` 等；CI 里跑一次 `migrate` 验证。

**P2-3 脚本硬编码别人的机器路径（本机直接跑必挂）**
- 证据：`build_web.sh` → `ROOT="D:/Undergraduate_courses/qiyekaifa/chongwupet"`、`NODE="C:/Users/asus/..."`；`start_all.sh` 同 + `D:/Redis`；`启动.bat` 指向 `D:\Undergraduate_courses\企业开发\期末作业\ruoyi-pet`。
- 建议：改为 `ROOT="$(cd "$(dirname "$0")" && pwd)"`，JDK/Node 走 `JAVA_HOME`/`node` 或 `.env`；`启动.bat` 用 `%~dp0` 相对路径。

**P2-4 零单元测试，验收脚本堆在根目录**
- 证据：`ruoyi/**/src/test` 下 0 个 Java 文件；35 个 `cdp_*` 脚本（34 个 .mjs + 1 个 .js）直接放仓库根，命名靠 `cdp_xxx_yyy`，无 runner、无断言库、大量重复代码。
- 建议：`tests/e2e/` 收拢，换 Playwright（自带 runner/断言/报告）；后端补 JUnit 覆盖三块高风险逻辑——匹配算法边界、权限门禁、支付幂等。

**P2-5 三个巨型单文件组件**
- 证据：`dashboard/index.vue` 1252 行、`match/index.vue` 1246 行、`home/index.vue` 756 行；无 ESLint/Prettier/TypeScript。
- 建议：拆 `components/dashboard/*`（趋势/分布/排行/动态/AI 洞察）、`composables/useMatchQuiz.js`；加 ESLint + Prettier + `vue-tsc`（可渐进）。

**P2-6 AI 依赖境外免费通道**
- 证据：默认 `https://text.pollinations.ai/v1`，无 key，随时限流/不可用；用户提问内容出境。

## 七、总评

- **功能广度**：★★★★☆ 18 个 C 端场景 + 18 个后台菜单，覆盖了"选—试—买—养—问—评"的大部分环节。
- **业务闭环**：★★☆☆☆ 宠物交易缺"下单/支付/交付/售后"，商品无中心、库存无概念。
- **技术设计**：★★★☆☆ 推荐算法与 AI 降级策略是亮点；但订单模型、模块划分、数据迁移欠账明显。
- **安全与合规**：★☆☆☆☆ Druid 公网 + 明文口令 + 弱 JWT，属于"能跑但不能上线"的状态。
- **工程化**：★★☆☆☆ 脚本硬编码、零单测、文档漂移，换人接手成本高。
